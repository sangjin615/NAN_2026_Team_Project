# 미지의 경매장 — AI 활용 기술

> 생성 모델은 표현하고 엔진은 판정한다 — 역할 분리, 2단계 생성, 자동 검증과 폴백

## 1. AI 활용 목적

**AI는 플레이어가 추론할 재료를 런마다 새로 만들고, 게임의 판단은 사람이 설계한
엔진에 남긴다.** 이 경계를 지키기 위해 생성 범위를 계약으로 못박고 결과를
자동으로 검증한다.

그렇게 나눈 이유는 이렇다. 미지의 경매장은 12일 동안 하루 8개, 총 96개 경매 LOT를 사용한다. 각 LOT에는 단순한 이름뿐 아니라 설명, 소문, 세트 힌트, NPC 반응과 시장 맥락이 필요하다. 모든 문구를 고정 작성하면 반복 플레이의 변화가 줄고, 무제한 생성에 맡기면 가격과 보상 같은 게임 규칙이 흔들릴 수 있다.

따라서 다음 목표로 AI를 사용했다.

1. 같은 게임 규칙 안에서 런마다 다른 추론 재료를 제공한다.
2. 반복 작성량을 줄이되 게임의 핵심 판단은 사람이 설계한 엔진에 남긴다.
3. AI 출력의 누락과 규칙 침범을 자동으로 검증한다.
4. API 장애나 형식 실패가 실제 플레이를 막지 않게 한다.

### AI를 쓴 두 층

이 프로젝트에서 AI는 성격이 다른 두 곳에 쓰인다. 문서 대부분은 앞쪽을 설명하지만
뒤쪽도 함께 밝힌다.

| | 런타임 생성 | 제작 단계 생성 |
|---|---|---|
| 언제 | **플레이할 때마다** | 개발 중 한 번 |
| 무엇 | LOT 설명·소문·세트 힌트·NPC 반응·사건·신문 리드 | 경매품 스프라이트 240개, 씬 배경, 타이틀곡 |
| 검증 | 스키마·ID·금지 수치·문구 품질을 매 호출 자동 검사 | 사람이 보고 채택 |
| 실패하면 | 항목 단위 재생성 → 공급자 교체 → 폴백 문구 | 다시 생성해 교체 |

**두 층 모두 결과물의 권리 조건을 확인하고 표기했다** (9장). 시각 에셋과 음악이
AI 생성이라는 사실은 감추지 않는다 — 이 게임은 AI로 만든 재료 위에서 AI가
계속 이야기를 채우는 구조이고, 그 경계를 사람이 설계한 엔진이 지킨다는 것이
이 문서의 요지다.

## 2. 설계 원칙: 생성 모델은 표현하고 엔진은 판정한다

| 엔진이 소유하는 값 | 생성 AI가 작성하는 내용 |
|---|---|
| 기준가·실제 가치 | 품목 표시 이름(`displayName`)·설명(`description`) |
| 등급·수요 계수 | 소문(`rumor`)·세트 힌트(`setHint`) |
| 보상·확률·배수 | NPC 반응(`npcReaction`) |
| 입찰·판매·대출·의뢰 규칙 | 런 전제(`premise`)·12일 시장 흐름(`marketArc`) |
| 승리·실패·파산 판정 | 세트 제목·공통 비밀·공개 힌트 |
| 12일 일정과 모든 ID | 세트 사건 제목·요약·신문 리드 |
| — | 당일 시장 헤드라인(`marketHeadline`) |

**생성 범위는 위 오른쪽 열이 전부다.** 의뢰 문구, 경매 진행 문구, 결산 요약,
엔딩 표현, 경쟁자 말투는 생성하지 않고 게임에 고정 작성되어 있다. 문서가
실제보다 넓게 읽히지 않도록 필드 이름을 함께 적었다.

이 경계 덕분에 모델이나 프롬프트가 바뀌어도 경제 규칙과 저장 데이터는 유지된다. 생성 결과에 `basePrice`, `trueValue`, `reward`, `multiplier`, `probability` 같은 금지 필드가 포함되면 검증에서 실패한다.

## 3. 2단계 생성 구조

### 3.1 런 시작 생성

게임 시작 시 한 번, **프레임 1회 + 세트 12회**로 나눠 호출한다.

| 호출 | 만드는 것 |
|---|---|
| 프레임 | 런 전제(`premise`), 12일 시장 흐름(`marketArc` — 날짜별 헤드라인과 분위기) |
| 세트 × 12 | 세트 제목, 공통 비밀, 공개 힌트, **과거 사건 제목·요약·신문 리드** |

세트 사건은 그 세트에 속한 물품 이름 둘 이상을 명시적으로 엮어 만든다. 이것이
플레이어가 세트를 추론하는 재료다.

**나눠 부르는 이유는 실패를 가두기 위해서다.** 한 번에 만들면 한 세트가
규칙을 어겨도 12개가 통째로 버려진다. 나눠 부르면 그 세트만 다시 만들고,
2회 재시도 후에도 안 되면 그 세트만 폴백으로 채운 뒤 나머지 11개를 살린다.

세트를 따로 만들면 사건이 서로 비슷해지므로, **이미 만든 사건 제목을 다음
호출의 프롬프트에 실어** 중복을 피한다. 실측에서 12개 세트의 사건 제목이
12/12 모두 달랐다.

모델은 엔진이 전달한 세트 ID를 추가하거나 변경할 수 없다.

### 3.2 일일 생성

하루치를 한 번에 만들고, 실패한 항목만 다시 만든다.

| 호출 | 만드는 것 |
|---|---|
| 하루치 1회 | 당일 시장 헤드라인(`marketHeadline`), 정확히 8개 LOT의 `displayName`·`description`·`rumor`·`setHint`·`npcReaction` |
| 복구 (필요할 때만) | 검증에 걸린 LOT 하나만 다시 |

현재 날짜가 진행될 때 **2일 뒤까지 미리 준비해** 플레이 중 대기를 줄인다.
저장 슬롯을 고르는 동안 런 blueprint가 완성되므로, 실제 플레이에서는 생성을
기다리는 시간이 거의 드러나지 않는다.

### 3.3 실패 처리

```text
엔진 입력 생성
→ 모델 호출
→ JSON·ID·필수 필드·금지 수치·문구 품질 검증
→ 실패한 항목만 골라 다시 만든다 (하루치 전체가 아니라 그 LOT 하나)
→ 그래도 실패하면 다음 공급자로 넘어간다
→ 모두 실패하면 사전 준비된 폴백 문구를 쓴다
→ 검증된 결과만 게임에 공급
```

**실패를 그 자리에 가둔다.** 예전에는 한 LOT이 규칙을 어기면 하루치가 통째로
버려졌다. 지금은 `dailyRepairIndices`가 고칠 자리만 골라 그 LOT만 다시 만들고,
나머지 결과는 살린다. 런 blueprint도 같은 방식으로 프레임과 12개 세트를 나눠
만들어, 한 세트가 실패해도 나머지 11개는 남는다.

**재시도해도 소용없는 실패는 즉시 접는다.** 401·403·429는 초 단위로 다시 불러도
같은 답이므로 그 공급자를 그 요청에서 포기하고 다음으로 넘어간다.

### 3.4 라우터 — 게임은 엔드포인트 하나만 안다

**게임은 어떤 모델을 쓰는지 모른다.** 공급자 선택·순서·타임아웃 배분·복구·폴백은
전부 AWS Lambda 라우터가 처리하고, 게임은 엔드포인트 하나에 JSON을 던진다.

**이렇게 만든 이유는 보안이다.** 배포본은 브라우저에서 도는 HTML이라 API 키를
들 수 없다. 실제로 빌드 단계에서 `assertPublicGenerationConfig`가 설정 파일에
`token`·`authorization` 같은 키가 있으면 빌드를 실패시킨다. 키는 Lambda 환경변수에만
있고 배포본에는 엔드포인트 주소만 박힌다.

#### 공급자 순서는 모드마다 다르다

| 모드 | 1순위 | 2순위 |
|---|---|---|
| 일자 생성 | `gpt-5.6-luna` | `gpt-4o-mini` |
| 런 blueprint | `gpt-4o-mini` | `gpt-5.6-luna` |

**측정으로 갈린 순서다.** 일자 생성에서 `gpt-4o-mini`는 두 번 연속 계약을
어겼고(`unsafe ending`·`does not match category`) 항목 복구를 거쳐도 통과하지
못했다. 반면 blueprint는 `gpt-4o-mini`가 네 번 다 성공했다. **실패가 확실한
공급자를 매번 먼저 태울 이유가 없다.**

blueprint 순서는 건드리지 않았다. 근거 없는 곳까지 바꾸면 다음에 문제가
생겼을 때 원인이 둘로 늘어난다.

#### 타임아웃은 게이트웨이 예산 안에서 나눈다

API Gateway 통합 타임아웃이 30초다. **두 공급자를 순차로 태우고도 그 안에
끝나야 한다.**

```text
일자 생성 :  luna 20초  +  mini 8초   =  28초
런 세트   :  조각이 작아 7~9초씩, 대신 13번 부른다
```

일자 생성은 성공 중앙값이 10.3초인데 상한을 20초로 둔 것은 꼬리 때문이다.
상한을 더 올리면 2순위를 태울 시간이 없어지고, 낮추면 느린 판이 그냥 죽는다.
blueprint는 13번 부르므로 상한을 키우면 총 시간이 게이트웨이를 넘는다.

#### 재시도가 무의미한 실패는 즉시 접는다

401·403·429는 초 단위로 다시 불러도 같은 답이다. 그런데 초기 구현은 LOT마다
재시도를 붙여 계속 두드렸고, 키가 잘못됐을 때 **일자 1건에 죽은 호출이 17건**
나갔다. 지금은 이 셋 중 하나가 나오면 그 공급자를 그 요청에서 접고 다음으로
넘어간다 — 17건에서 최대 5건으로 줄었다.

접는 쪽을 고른 이유가 하나 더 있다. 계속 두드려서 나오는 결과물은 **대부분이
폴백 문구인데 헤더에는 그 공급자 이름이 찍힌 응답**이다. 실측에서 한 공급자가
정확히 그것을 만들었다(8개 중 2개만 생성). 그럴 바에는 다음 공급자에게 기회를
주는 편이 낫다.

#### 뺀 공급자도 기록한다

무료 등급 공급자 하나를 1순위로 붙였다가 뺐다. 조직 단위 분당 토큰 한도에
걸려 8개 중 6개가 폴백으로 채워졌고, 모델을 더 작은 것으로 바꿔도 같은 한도에
걸렸다. **모델 교체로 우회되는 문제가 아니라 이 구조의 토큰 유입을 감당하지
못하는 것이었다.**

코드는 지우지 않고 환경변수 한 줄로 되살릴 수 있게 남겼다. 설계 결정이 아니라
용량 제약이므로 조건이 바뀌면 되돌릴 수 있어야 한다.

## 4. VSL, 게임 엔진, AI, Team Loop의 역할

### VSL

씬 목록, 화면 플로우, 좌표와 크기, UI 요소, 사운드와 전환의 골격을 만든다. 최종 VSL 결과는 어댑터와 매핑 파일을 통해 게임 상태에 연결한다.

### 게임 엔진

12일 일정, 96개 LOT, 입찰, 판매, 의뢰, 대출, 파산, 결산과 최종 유물 경매를 결정론적으로 처리한다. 같은 시드면 같은 일정과 같은 판정이 나온다.

### 생성 AI

엔진이 확정한 구조와 ID를 바꾸지 않고 플레이어에게 보이는 표현 콘텐츠를 채운다.

### Team Loop와 검증 하네스

생성 결과가 스키마, ID, 개수와 역할 경계를 지키는지 검사하고, 게임 회귀 테스트까지 함께 실행한다. 도구 자체가 게임의 주인공은 아니며, AI 생성물을 실제 게임에 안전하게 연결하기 위한 제작 안전장치다.

### 사람

위 넷은 모두 도구다. **사람은 무엇을 만들지 정하고, 나온 결과를 보고 다음을
정한다.**

이 프로젝트에서 사람과 AI의 분업은 이렇게 갈렸다.

| 사람이 한 것 | AI가 한 것 |
|---|---|
| 무엇이 필요한지 묻고 정한다 | 코드를 쓴다 |
| 나온 결과를 보고 받아들일지 정한다 | 측정 도구를 만들고 돌린다 |
| 어긋난 곳을 지적하고 방향을 돌린다 | 문서와 인수인계를 쓴다 |
| 무엇을 포기할지 정한다 | 대안과 근거를 제시한다 |

**이 방식이 성립하려면 검증이 자동이어야 한다.** 사람이 코드를 한 줄씩 읽어
확인하지 않기 때문이다. 그래서 이 프로젝트는 판단이 필요한 자리마다 기계가
읽을 수 있는 근거를 남기도록 만들었다 — 생성 결과는 검증기가, 게임 규칙은
테스트 109건이, 연결 지점은 `npm run audit`이, 성능과 품질은 배포본에 직접
요청을 보내는 측정 도구가 확인한다.

**측정이 사람의 판단을 뒤집은 적도 있다.** 스키마를 줄인 뒤 8판을 재고
"지연이 좋아졌다"고 판단했는데, 8판을 더 재니 뒤집혔다(7.6). 사람이 코드를
읽어서가 아니라 숫자가 늘어서 틀린 것이 드러났다. 이 문서의 수치를 신뢰할 수
있는 이유도 같다.

**한계도 분명하다.** 사람이 구현 세부를 직접 읽지 않으므로, 검증이 보지 않는
영역은 늦게 발견된다. 실제로 로딩 화면이 3픽셀로 찌그러져 보이지 않던 결함이
있었는데, 테스트도 검증기도 이것을 잡지 못했고 브라우저로 직접 열어본 뒤에야
드러났다. **자동 검증은 계약을 지키지만 "보기에 맞는가"는 지키지 못한다.**

## 5. 사용 도구와 활용 내역

### 5.1 게임 안에서 도는 것 (플레이할 때마다 실행)

| 도구 / 모델 | 버전 | 무엇을 하는가 |
|---|---|---|
| OpenAI `gpt-5.6-luna` | 모델명이 버전 | 일자 생성 1순위. 하루 8 LOT의 설명·소문·세트 힌트·NPC 반응을 만든다 |
| OpenAI `gpt-4o-mini` | 모델명이 버전 | 런 blueprint 1순위 겸 일자 생성 2순위. 12일 시장 흐름과 세트 사건을 만든다 |
| AWS Lambda + API Gateway | Node.js 22 런타임 · 512MB | 위 두 모델을 감싸는 라우터. 공급자 순서·타임아웃 배분·항목 단위 복구·폴백을 여기서 처리한다. 게임은 이 엔드포인트 하나만 안다 |

**게임 자체에는 런타임 의존성이 없다.** 브라우저 표준 API만 쓰고, 위 호출도
`fetch` 하나다.

## 6. 주요 프롬프트 및 계약 방식

장문의 자연어 지시를 매번 전달하는 대신, 고정 규칙을 **하나의 계약서 파일**로
모았다. 파일은 `Runtime/contracts/compact-generation-contract.txt` 하나뿐이고,
검증기(`generation-server.js`)가 같은 파일을 근거로 결과를 검사한다. **지시와
검사가 갈라지지 않도록 계약을 두 곳에 두지 않는 것이 원칙이다.**

### 6.1 계약서를 절로 쪼개 필요한 것만 보낸다

**계약서를 모드별 절로 나눠 필요한 것만 보내자 한 판 입력이 30.4% 줄었다.**
파일은 하나로 유지해 지시와 검사가 갈라질 여지를 두지 않았다.

계약서에는 `@ALL` · `@RUN` · `@DAY` 표식이 있고, 호출 모드에 따라 공통 절과
해당 모드 절만 조립해 보낸다.

```text
@ALL   227자   JSON·한글 규칙, ID 보존, 시대 배경
@RUN   887자   런 스키마, 세트 사건 규칙            → 런 호출에는 1,114자
@DAY 1,116자   일자 스키마, 길이·어미·카테고리 어휘 → 일자 호출에는 1,343자
```

**왜 필요했나.** 생성을 항목 단위로 쪼개자 호출 수가 늘었고, 쪼개기 전에는 한 번
실렸던 계약서가 한 판에 121번 실리게 되었다. 그때 계약서가 전체 입력의 74%를
차지했고, 그중 상당량은 그 호출에 쓸 일이 없는 규칙이었다 — LOT 하나를 만드는
호출이 세트 사건 규칙 695자를 매번 날랐다.

절을 나눈 뒤 **한 판 입력이 30.4% 줄었다.** 파일은 여전히 하나여서 갈라질
여지가 없고, 표식이 없는 계약서를 만나면 전부 `@ALL`로 들어가 예전과 같이
동작한다.

**표식 오타는 조용히 규칙을 지운다.** 어느 절에도 실리지 않은 줄이 생기면 모델은
규칙이 사라진 줄 모르고 답하고 검증기만 뒤늦게 떨어뜨린다. 그래서 **모든 줄이
적어도 한 모드에 실리는지 테스트가 확인한다.**

### 6.2 실제 계약서 (일자 생성 부분)

요약이 아니라 모델에게 그대로 가는 문장이다.

```text
Return one JSON object only. Write every user-facing text value in Korean.
Never output numeric game rules. Copy IDs exactly and preserve input order.

DAY: {schemaVersion:"1.0",day,marketHeadline,
      lots:[exactly 8 {lotId,displayName,description,rumor,setHint,npcReaction}]}.
Daily limits per item: displayName 20 Korean characters, description 70,
rumor 45, setHint 25, npcReaction 45. Use one sentence per text field.
Copy each input baseName exactly into displayName. Describe only visible
material, engraving, discoloration, repair, provenance mark, or wear.
Description must be one factual observation ending with one of:
"남아 있다.", "보인다.", "확인된다.", "이어진다.", "드러난다."
Vary the observed feature across all eight items and do not reuse the same
phrase three times. Never claim magic, supernatural powers, translation,
navigation, appraisal, market value, or gameplay effects as fact.
Category vocabulary: CER uses 유약/굽/몸체/손잡이/뚜껑/항아리/도자;
CLK uses 문자판/바늘/태엽/케이스/시계/크로노미터/유리돔/골격; ...
Describe the artifact, not the person or place depicted by its name.
```

### 6.3 실제로 무엇이 나오는가

**계약이 지키는 것은 형식이고, 값이 나오는 것은 내용이다.** 아래는 배포된
엔드포인트가 실제로 만든 세트 하나다. 손대지 않은 그대로다.

| 필드 | 생성 결과 |
|---|---|
| 세트 제목 | 공회와 은밀한 유물 |
| 공통 비밀 | 두 개의 보석이 한 번의 사건을 묘사한다. |
| 공개 힌트 | 티아라와 반지가 같은 날 만들어졌다. |
| 사건 제목 | 티아라와 반지의 은밀한 연결 |
| 사건 요약 | 티아라와 반지는 한 명의 장금사가 제작한 것으로 확인되었다. 그는 두 개의 보석을 서로 다른 주문자에게 판매했지만, 그 둘은 이후 한 번의 사건에서 연결되었다. |
| 신문 리드 | 티아라와 반지의 연관성, 한 명의 장금사가 그 비밀을 알고 있다. |

**여기서 계약이 강제한 것은 셋이다.** 사건이 세트에 속한 물품 이름 둘 이상을
명시적으로 엮을 것, 마법·유령·예언 같은 초자연을 쓰지 않을 것, 가격·보상·확률을
쓰지 않을 것. 실제로 "장금사가 두 주문자에게 팔았다"는 평범한 인간사이고
수치가 하나도 없다.

**신문 리드가 요약을 베끼지 않는 것도 계약이다.** 같은 사건을 다른 각도에서
쓰게 해 플레이어가 두 번 읽을 이유를 만든다.

LOT 쪽 결과는 7.4에 런 두 개를 나란히 놓았다.

### 6.4 형식은 지시가 아니라 검증기가 잡는다

문장으로 "마침표는 하나" 같은 형식을 지시해 봤지만 **이전과 같은 비율로 어겼다
(8건 중 1건).** 그래서 형식 강제는 프롬프트에서 빼고 검증기에 맡겼다.

검증기가 보는 것은 스키마·ID·개수·금지 수치에 더해 문구 품질이다 — 길이 초과,
허용 밖 어미, 카테고리 어휘 불일치, 한 문장 위반, 여덟 항목 간 중복이 모두
자동으로 걸린다. 걸린 항목은 6.5의 복구 호출로 넘어간다.

### 6.5 복구는 실패한 항목에만 보낸다

전체를 다시 만들지 않고 그 LOT 하나만 다시 만든다. 복구 프롬프트에는 **어긴
규칙과 그 LOT 입력만** 싣는다.

```text
RETRY_ERRORS:
lot 5 description has unsafe ending
<해당 모드의 계약 절>
INPUT LOT: {lotId, baseName, category, grade, setId}
```

실측에서 8개 중 6개가 이 경로로 살아났다. 하루치를 통째로 버리던 때와 비교하면
같은 실패에서 건지는 양이 다르다.

## 7. 측정 결과

모든 수치는 **배포된 엔드포인트에 실제로 요청을 보내** 얻었다. 시뮬레이션이나
추정이 아니다. 측정일은 2026-08-07~08이다.

### 7.1 배포 API 성공률과 지연

**24판 중 23판이 실제 생성으로 돌아왔고, 계약 검증 실패는 0건이다.** 남은
1판도 게임이 멈추지 않고 폴백 문구로 이어졌다.

일자 생성(하루 8 LOT)을 시드만 바꿔 순차로 24판 호출한 결과다.

| 지표 | 결과 |
|---|---|
| 실제 생성 | **23 / 24판** |
| 폴백으로 내려간 판 | 1 / 24 |
| **계약 검증 실패** | **0 / 24판** |
| 지연 중앙값 | **10.3초** |
| 지연 범위 | 8.0 ~ 20.1초 |

런 blueprint(프레임 + 세트 12개)는 15.1초에 완료되었고, 12개 세트의 사건 제목이
**12/12 모두 서로 달랐다** — 세트를 나눠 만들 때 이미 쓴 제목을 프롬프트에
실어 중복을 피하는 장치가 동작한다.

**폴백으로 내려간 1판의 사유도 로그로 확인했다.** 공급자 두 곳이 모두 응답
시간을 넘긴 경우였고(20초·8초), 인증 오류나 계약 위반이 아니었다.

### 7.2 입력량 감축

**같은 결과를 얻는 데 드는 입력을 두 차례 줄여, 한 판 기준 계약서에서 30.4%·
스키마에서 15%를 덜어냈다.** 줄인 뒤 다시 재어 계약 준수가 나빠지지 않은 것도
확인했다.

| 조치 | 효과 |
|---|---|
| 계약서를 모드별 절로 분리 | 한 판 입력 **30.4% 감소** |
| 스키마의 항목 정의 반복 제거 | 일자 스키마 3,997 → **798자 (80% 감소)** |
| 〃 | 런 스키마 6,248 → **1,126자 (82% 감소)** |

두 번째 조치는 스키마가 8개 LOT의 정의를 여덟 번 반복하던 것을 하나로 합친
것이다. 일자 호출 하나가 6,117 → 2,918자가 되었고, **한 판 전체 입력이 약 15%
더 줄었다.** 줄인 뒤 16판을 다시 재어 계약 준수가 나빠지지 않았음을 확인했다.

### 7.3 폴백 품질

**폴백 문구의 중복이 구조적으로 사라졌다 — 600일치 검사에서 하루 안 중복 0건,
계약 검증 실패 0건이다.** 예전에는 매일 최소 두 쌍이 글자 그대로 같았다.

AI가 실패해도 게임이 멈추지 않는 것은 이전부터 확인된 사실이다. 이번에 새로
잰 것은 **폴백으로 나오는 문구 자체의 품질**이다.

| 지표 | 이전 (문자열 조합) | 현재 (사전 준비 문구) |
|---|---|---|
| 하루 8 LOT 중 중복 설명 | **매일 최소 2쌍** | **0건** |
| 하루 평균 서로 다른 문장 어미 | 2가지 | **3.99가지** |
| 하루 평균 서로 다른 첫머리 | — | **7.26 / 8** |
| 계약 검증 실패 | 0 | **0 / 600일** |

50개 시드 × 12일 = **600일치**를 검사한 결과다. 실제 생성의 어미가 8판 평균
4.6가지이므로, **폴백이 실제 생성에 근접한 다양성을 낸다.**

#### 폴백 문구를 어떻게 만들었나

**새로 지어내지 않았다. 지난 실제 생성물을 재활용했다** — 이미 비용을 치렀고
계약을 통과한 문장들이다. 거르는 단계가 넷이다.

1. **실제 검증기로 검사한다.** 후보를 여덟씩 묶어 `qualityErrors`에 그대로
   먹이고 걸린 자리만 버린다. 카테고리 어휘·어미·한 문장 규칙이 모두 그 함수에
   있으므로 여기서 다시 적으면 갈라진다
2. 어미만 다른 중복은 줄기 기준으로 하나만 남긴다
3. 카탈로그 60종 품목 이름이 든 문장은 버린다
4. **품목 머리 명사가 든 문장은 예비로 강등한다** — "소금단지의 뚜껑에"가
   청자 항아리에 붙는 것을 막는다

**3·4단계는 실제 사고에서 나왔다.** 배포 후 확인에서 청자 항아리에 "제비문이
찻잔의 손잡이에 새겨져 있고"가 붙었다. 찻잔은 카탈로그에 없는, 모델이 지어낸
사물이라 이름 목록으로는 안 걸렸다. 조사가 붙은 형태로만 거르는 목록을 따로
두어 해결했다.

카테고리마다 문장이 모자라면 **그 카테고리만 8개인 하루를 만들어** 배포본에
보내 채웠다. 회화가 6개뿐이던 것을 65개로 늘리는 식이다.

**남은 한계도 적는다.** 카테고리 단위로 돌려쓰므로 황동 물건에 은제 설명이
붙는 재질 어긋남은 남는다. 품목별로 은행을 나누면 없앨 수 있지만 그러면 문장
수가 모자란다. **지금 것은 100% 티가 나던 예전 템플릿보다 낫되 완전하지는
않다.**

### 7.4 런마다 달라지는가 — 같은 품목, 다른 런

**같은 품목이 런마다 다른 설명·소문·세트 힌트를 받는다.** 1장에서 세운 첫
목표가 실제로 지켜지는지 시드만 바꿔 1일차를 두 번 생성해 확인한 결과다.

**엔진의 몫 — 일정 구성이 달라진다.** 8개 LOT 중 겹친 품목은 2개뿐이었다.

**생성의 몫 — 겹친 품목조차 다른 문장을 받는다.** 이쪽이 핵심이다.

> **붉은 장갑의 배우** (두 런에 모두 등장)
>
> | | 런 A | 런 B |
> |---|---|---|
> | 설명 | 액자 안쪽에 벗겨진 안료와 얇은 덧칠 자국이 남아 있다. | 화폭 가장자리에 붉은 안료가 번졌고 액자에 작은 보수 흔적이 남아 있다. |
> | 소문 | 무대 뒤에서 급히 손질했다는 말이 있다. | 초연 직후 극장 관리인이 맡겼다는 소문이 있다. |
> | 세트 힌트 | 붉은 색조 그림의 연결점 | 무대 초상화 연작 |

> **항로문 금은 상감함**
>
> | | 런 A | 런 B |
> |---|---|---|
> | 설명 | 황동 표면의 은제 상감선 사이로 어두운 녹이 확인된다. | 금속 표면에 금은 상감 선과 옅은 녹이 남아 있다. |

> | 세트 힌트 | 금속 공예품 사이의 빈 고리 | 금속 공예품과 어울림 |

**세트 힌트가 달라지는 것이 게임에는 가장 크다.** 플레이어는 이 문구로 어떤
물품끼리 묶이는지 추론하므로, 같은 물품이라도 런마다 다른 실마리를 준다.

**덜 달라지는 것도 있다.** 시장 헤드라인은 두 런이 거의 같았다 — "안개 속
경매장에 오래된 항구의 흔적이 모였다" 와 "안개 낀 경매장에 항구의 오래된 흔적이
모인다." 하루에 하나뿐인 필드라 표현 폭이 좁고, LOT 문구만큼 갈리지 않는다.

### 7.5 게임 및 하네스 검증

- 게임 런타임 테스트 **109건 전부 통과**
- 생성 연결 점검(`npm run audit:generation`) 오류 0건
- 900개 시드에서 86,400 LOT 일정 생성, 잘못된 12일 일정 0건
- 생성 결과의 엔진 소유 수치 침범 0건
- 브라우저에서 배포본을 열어 런 blueprint와 1~3일차 생성 수신까지 확인

### 7.6 수치 해석의 한계

**표본이 작다.** 24판은 통계가 아니라 관찰이다. 실제로 이 프로젝트는 같은
함정을 한 번 겪었다 — 스키마를 줄인 뒤 8판을 재고 "지연 중앙값이 10.9초에서
9.4초로 좋아졌다"고 적었는데, 8판을 더 재니 11.4초가 나와 합친 중앙값이
10.3초였다. **8판으로 성능 변화를 단정할 수 없다는 것이 이 과정에서 확인한
사실이고, 위 표의 지연 수치도 같은 눈으로 읽어야 한다.**

그래서 주장하지 않는 것과 주장하는 것을 나눈다.

- **주장하지 않는다** — 지연이 개선되었다, 폴백률이 낮아졌다
- **주장한다** — 입력량이 줄었고(측정 가능), 계약 준수가 24판 내내 깨지지
  않았으며(0/24), 폴백 문구의 중복이 구조적으로 사라졌다(600일 검사)

## 8. 실제 프로젝트에 미친 영향

### 적용 전

- UI 목업, 기획 문서와 밸런싱 자료가 실제 게임 상태와 분리되어 있었다.
- 생성 AI 요청·응답의 명시적 계약과 실패 처리 방식이 없었다.
- VSL 최종 결과를 받기 전에는 시스템 연결 작업을 시작하기 어려웠다.

### 현재

- VSL과 무관하게 12일 진행을 검증할 수 있는 모듈형 런타임이 존재한다.
- 경매·판매·의뢰·경제·대출·결산이 같은 상태 데이터를 공유한다.
- VSL 요소를 교체할 어댑터와 좌표 매핑 계약이 준비되어 있다.
- 생성·검증·재시도 경로를 실제 모델로 확인했다.
- AI가 없어도 폴백으로 12일 진행이 중단되지 않는다.

### 무엇이 이 속도를 만들었나

이 프로젝트에서 실제로 효과가 컸던 것은 특정 모델이 아니라 **판단할 때마다
근거를 남기게 만든 구조**였다.

- **계약을 한 곳에만 둔다.** 지시와 검사가 같은 파일을 보므로 갈라지지 않는다.
  실제로 검증기를 복제해 둔 도구 하나가 계약에 없는 필드를 계속 요구해 옳은
  결과를 떨어뜨린 적이 있고, 그 뒤로 복제를 금지했다
- **실패를 항목 단위로 가둔다.** 한 LOT의 실수가 하루치를 버리지 않는다
- **결정을 문서에 남긴다.** 되돌린 이유, 틀린 판단, 표본이 모자라 단정하지 못한
  것까지 적는다. 다음 사람이 같은 실험을 반복하지 않기 위해서다
- **눈으로 볼 것은 눈으로 본다.** 자동 검증이 닿지 않는 영역이 있다는 것을
  결함 하나로 배웠다(4장)

**쓰지 않기로 한 것도 있다.** 팀은 이 게임과 별개로 오케스트레이션과 루프
엔지니어링 두 갈래의 제작 도구를 만들어 왔고, **둘은 Team Loop 하나로 합쳐졌다**
— 갈라져 있던 융합 브랜치가 지금은 본류다. 그러나 그 전체를 이 게임에 적용하려면
마감 안에 끝나지 않는다고 판단해 **밸런스 실험 엔진 한 가지만 떼어 썼다.**
파이프라인과 워크플로 구상도 세웠지만 같은 이유로 이번 범위에서 접었다.

도구를 더 넣는 것이 항상 이득은 아니다. 이번에 실제로 값을 한 것은 계약·검증·
측정처럼 **결과를 확인해 주는 장치**였고, 그 밖의 자동화는 마감이라는 제약
앞에서 비용이 더 컸다.

**남은 과제도 같은 자리에 있다.** 폴백 문구는 카테고리 단위로 재사용하므로
드물게 물품과 어긋난 표현이 나올 수 있고, 표본이 작아 단정하지 못한 수치가
아직 몇 개 남아 있다. 문서에 그대로 표시해 두었다.
