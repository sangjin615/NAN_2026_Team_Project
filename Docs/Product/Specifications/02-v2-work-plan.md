## 태스크 상세 — 정확히 무엇을 하는가

### C00 씬 플로우 목업

- 할 일: ① 씬 목록 확정 — 타이틀 → 런 시작 브리핑(도시·목표) → 도시 지도 → 거점별 씬(경매 카탈로그 / 경매 진행 / 판매 / 감정 / 하루 정산) → 사건 → 상회 평가 → 최종 특별 경매 → 전시관·런 결과. ② 각 씬을 더미 데이터로 채워 클릭 전환만 되게 구현. ③ 씬 전환 조건 표 작성(무엇을 하면 다음 씬이 열리는가). ④ 하루 행동 구조 제안 1쪽 — 이 플로우가 암묵적으로 정하는 "하루에 몇 번, 어떤 방식으로 행동하는가"를 명시적 제안으로 뽑아낸다.
- 산출물: 단일 HTML 목업 + 전환 조건 표 + 하루 구조 제안서
- 완료: 런 시작~결과까지 전 씬 전환 가능, GD_JM 승인 기록. 세라핀 화면 구조 재사용 금지.

### K01~K08 (GD_JM)

- **K01**: C00의 하루 구조 제안을 심사한다. 검토 항목 — 런 일수 N(후보 7~14), 하루 행동 횟수, 슬롯 vs 포인트 방식, 씬 전환 조건의 타당성. 승인/수정 지시 후 `docs/decisions/007`로 기록(선택안·이유·기각 대안·재검토 조건 필수).
- **K02**: 시작 자본, 상회 단계별 거래 단위 표(§9.2), 최종 유물 가격, 배율(후보 50~100배)을 확정해 `008`로 기록. E측 수치 메모(구 E01)를 근거로 사용.
- **K03**: E02 실행 **전에** 판정 기준을 수치로 문서화. 최소 포함: ① 현금 비축 전략 봇이 전체 전략 중 상위 몇 %면 실패인지(제안: 20%) ② 목표 자산 도달률 허용 범위 ③ 생성판 간 난이도 편차 허용치. 007 또는 별도 문서에 기록.
- **K04**: `00-product-spec.md` 헤더에 지위 표기(폐기 or "경매 층 §9~13 참조용") + 결정 문서 한 줄.
- **K05**: 엔딩 3종(MVP: 성공·중립·파산)의 판정식 — 입력이 되는 성장 축 목록, 가중치, 주요 사건 플래그 반영 방식, 경계값. E06 구현 전 확정.
- **K06**: C04 초안 6종을 검수. 기준 — 계열 균형(수집 목표가 되는가), 희귀도 단계 구분, 이름·설정의 톤. 확정 목록을 스펙 §12.2에 반영 지시.
- **K07**: 도전과제 8종과 해금 보상 짝을 확정. 기준 — 운이 아니라 운영 방식 선택을 측정하는가, 보상이 경제 능력치가 아닌가.
- **K08**: 플레이테스트 설계(질문지는 스펙 §16.2 기반) → 진행 → 006 재검토 조건 3종(돈 번 감각·성장 체감·재도전 의사) 판정 리포트 작성. 실패 시 재검토 발동.

### E 태스크 (최재혁)

- **선행: B02·OPS2 리뷰 마감**: 둘 다 REVIEW 상태. 승인 처리하고 OPS2(005 분리 지도)는 상태를 "결정"으로 확정 — E03의 입력이다.
- **E03 모듈 분리**: 005 지도의 함수→모듈 매핑대로 engine.js를 물리 분리(동작 불변). build.py 로드 순서 갱신, `python public/auction/build/build.py` 재실행, 회귀·스모크 그린 확인. 순환 참조 발견 시 005 문서를 먼저 수정.
- **E02 시뮬레이터 — 구축**: 헤드리스 Node 스크립트. 구성 — ① 전략 프로파일 봇(최소 3종: 현금 비축형 / 균형형 / 공격 매입형) ② N일 루프(경매 매입 → 판매 → 유지비) ③ 가격 모델(추정 오차, 구매자 제안 공식, 수수료) ④ 파라미터 입력(시작 자본·수익률·유지비 — K02 값) ⑤ 출력(전략별 최종 자산 분포, 자산 곡선, 시드 간 편차). 시드 고정 재현 필수.
- **E02 — 실행·판정**: K01·K02·K03 확정 후 1,000런 이상 돌려 K03 기준선 대비 판정 리포트 작성. 특히 "물건을 안 사는 전략"이 이기면 여기서 정지.
- **씬-기능 매핑 설계** (C00 확정 후, E04의 선행 산출물): C00의 씬마다 — 필요한 엔진 API, 데이터 스키마, 스펙 근거 조항(§3~§12), 소속 모듈을 표로 정리. 이 표가 E04~E07의 구현 명세가 된다.
- **E04 런 상태 머신**: 상태(일차·하루 국면·거점 진입 상태), 전환 규칙, 기간 만료 → 상회 평가 진입, 파산 조기 종료, 런 상태 저장/복원. 매핑 설계표대로 구현.
- **E05 판매 시장**: 구매자 생성(취향 태그·지위·해금 조건), 제안가 공식(기본율 + 취향 일치 보너스 + 시장 사건 보정 + 지터), 보관 물건의 다음 날 재등장, 계열 일괄 판매 프리미엄. 프로토타입의 구조만 참조하고 수치는 E02 모델과 일치시킨다.
- **E06 상회 성장·엔딩**: 성장 축 데이터 구조, 단계 1→2 승급 조건, K05 판정식 구현. **엔딩 확정이 최종 경매보다 먼저 실행되는 순서를 코드로 보장**(스펙 §2.2).
- **E07 최종 경매·유물**: 엔딩 등급 → 출품 유물 풀 선택, 상위 자금 봇 구성, 낙찰/실패 처리(실패해도 런 실패 아님), 유물·획득 런 메타를 계정 저장소에 영구 기록.
- **E08 검증 하네스**: 생성물 JSON 스키마 검증기 — 태그 존재·가격 범위·계열 일관성·숨은 태그 직접 노출 여부 검사. 실패 시 예비 프리셋 폴백(최소 2종). C07 스키마와 왕복하며 확정.
- **E09 밸런싱·회귀**: K08 피드백 반영 패치. 모든 패치 후 회귀·스모크 그린 유지.

- **C01 보드 상세 분해**: 각 태스크에 allowedPaths·검증 프로필을 부여하고 누락 태스크를 제안. 004 규약(참고 파일 명시) 준수 확인.
- **C02 거점 화면**: C00 골격에 실제 게임 상태를 바인딩 — 도시 지도 + 상회·경매장·거래소·감정소 4종. 거점 배지(할 일 표시)와 "이동 무료, 행동만 소비" 규칙 반영.
- **C03 판매 UI**: 물건별 구매자 제안 나열 — 제안가, 매입가 대비 손익, 취향 일치 표시, 판매/보관 선택. E05 API 기준.
- **C04 유물 6종 초안**: 각 유물당 — 이름, 계열(2계열 × 3개 권장), 희귀도, 설정 4~6줄, 해금 콘텐츠 아이디어 1개. K06 검수로 제출. 버려질 각오로 과감하게.

- **C06 사건 연출**: 엔진이 주는 사건 데이터(조건·효과)를 카드형 UI로 렌더. 선택 결과가 엔진 상태에 반영되는 것 확인. 표현만 담당, 판정 로직 금지.
- **C07 생성 프롬프트·스키마**: 런 일괄 생성용 프롬프트 + 구조화 출력 JSON 스키마(도시·NPC·물건·사건·소문). 숨은 태그 직접 서술 금지 규칙 포함. E08 하네스를 통과하는 샘플 3개 제출이 완료 조건.
- **C08 도전과제·복기**: 도전과제 목록·달성 표시 화면 + 런 복기 리포트(주요 거래별 매입가/판매가/판단 근거 추적). K07 확정 목록 기준.
