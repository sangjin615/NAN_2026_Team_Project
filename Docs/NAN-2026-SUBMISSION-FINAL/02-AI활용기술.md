# 미지의 경매장 — AI 활용 기술

> 생성 모델은 표현하고 엔진은 판정한다 — 역할 분리, 2단계 생성, 자동 검증과 폴백

## 1. AI 활용 목적

미지의 경매장은 12일 동안 하루 8개, 총 96개 경매 LOT를 사용한다. 각 LOT에는 단순한 이름뿐 아니라 설명, 소문, 세트 힌트, NPC 반응과 시장 맥락이 필요하다. 모든 문구를 고정 작성하면 반복 플레이의 변화가 줄고, 무제한 생성에 맡기면 가격과 보상 같은 게임 규칙이 흔들릴 수 있다.

따라서 다음 목표로 AI를 사용했다.

1. 같은 게임 규칙 안에서 런마다 다른 추론 재료를 제공한다.
2. 반복 작성량을 줄이되 게임의 핵심 판단은 사람이 설계한 엔진에 남긴다.
3. AI 출력의 누락과 규칙 침범을 자동으로 검증한다.
4. API 장애나 형식 실패가 실제 플레이를 막지 않게 한다.

### AI를 쓴 두 층

이 프로젝트에서 AI는 성격이 다른 두 곳에 쓰인다. 문서 대부분은 앞쪽을 설명하지만
뒤쪽도 함께 밝힌다.

| | 런타임 생성 | 제작 단계 생성 |
|---|---|---|
| 언제 | **플레이할 때마다** | 개발 중 한 번 |
| 무엇 | LOT 설명·소문·세트 힌트·NPC 반응·사건·신문 리드 | 경매품 스프라이트 240개, 씬 배경, 타이틀곡 |
| 검증 | 스키마·ID·금지 수치·문구 품질을 매 호출 자동 검사 | 사람이 보고 채택 |
| 실패하면 | 항목 단위 재생성 → 공급자 교체 → 폴백 문구 | 다시 생성해 교체 |

**두 층 모두 결과물의 권리 조건을 확인하고 표기했다** (9장). 시각 에셋과 음악이
AI 생성이라는 사실은 감추지 않는다 — 이 게임은 AI로 만든 재료 위에서 AI가
계속 이야기를 채우는 구조이고, 그 경계를 사람이 설계한 엔진이 지킨다는 것이
이 문서의 요지다.

## 2. 설계 원칙: 생성 모델은 표현하고 엔진은 판정한다

| 엔진이 소유하는 값 | 생성 AI가 작성하는 내용 |
|---|---|
| 기준가·실제 가치 | 품목 표시 이름·설명 |
| 등급·품질·수요 계수 | 소문·세트 힌트 |
| 보상·확률·배수 | NPC 반응·경쟁자 말투 |
| 입찰·판매·대출 규칙 | 의뢰 제목·플레이버 문구 |
| 승리·실패·파산 판정 | 감정·경매·결산 표시 문구 |
| 12일 일정과 모든 ID | 유물 설정·엔딩 표현 |

이 경계 덕분에 모델이나 프롬프트가 바뀌어도 경제 규칙과 저장 데이터는 유지된다. 생성 결과에 `basePrice`, `trueValue`, `reward`, `multiplier`, `probability` 같은 금지 필드가 포함되면 검증에서 실패한다.

## 3. 2단계 생성 구조

### 3.1 런 시작 생성

게임 시작 시 한 번 생성한다.

- 12일 시장 흐름과 분위기
- 입력된 세트 ID별 제목, 공통 비밀, 공개 힌트
- 경쟁자별 말투와 첫 등장 문구
- 유물별 표시 이름과 설정
- 성공·실패·파산 엔딩 표현

모델은 엔진이 전달한 세트·경쟁자·유물 ID를 추가하거나 변경할 수 없다.

### 3.2 일일 생성

매일 필요한 콘텐츠를 생성한다.

- 정확히 8개 LOT의 표시 이름, 설명, 소문, 세트 힌트, NPC 반응
- 당일 제공되는 의뢰 ID별 제목과 플레이버 문구
- 감정 안내·성공·주의 문구
- 경매 시작·재입찰·낙찰·패찰 문구
- 하루 결산 요약

현재 날짜가 진행될 때 2일 뒤까지 준비하여 플레이 중 대기를 줄이는 구조다.

### 3.3 실패 처리

```text
엔진 입력 생성
→ 모델 호출
→ JSON·ID·필수 필드·금지 수치·문구 품질 검증
→ 실패한 항목만 골라 다시 만든다 (하루치 전체가 아니라 그 LOT 하나)
→ 그래도 실패하면 다음 공급자로 넘어간다
→ 모두 실패하면 사전 준비된 폴백 문구를 쓴다
→ 검증된 결과만 게임에 공급
```

**실패를 그 자리에 가둔다.** 예전에는 한 LOT이 규칙을 어기면 하루치가 통째로
버려졌다. 지금은 `dailyRepairIndices`가 고칠 자리만 골라 그 LOT만 다시 만들고,
나머지 결과는 살린다. 런 blueprint도 같은 방식으로 프레임과 12개 세트를 나눠
만들어, 한 세트가 실패해도 나머지 11개는 남는다.

**재시도해도 소용없는 실패는 즉시 접는다.** 401·403·429는 초 단위로 다시 불러도
같은 답이므로 그 공급자를 그 요청에서 포기하고 다음으로 넘어간다.

## 4. VSL, 게임 엔진, AI, Team Loop의 역할

### VSL

씬 목록, 화면 플로우, 좌표와 크기, UI 요소, 사운드와 전환의 골격을 만든다. 최종 VSL 결과는 어댑터와 매핑 파일을 통해 게임 상태에 연결한다.

### 게임 엔진

12일 일정, 96개 LOT, 입찰, 감정, 판매, 의뢰, 대출, 파산, 결산과 유물 경매를 결정론적으로 처리한다.

### 생성 AI

엔진이 확정한 구조와 ID를 바꾸지 않고 플레이어에게 보이는 표현 콘텐츠를 채운다.

### Team Loop와 검증 하네스

생성 결과가 스키마, ID, 개수와 역할 경계를 지키는지 검사하고, 게임 회귀 테스트까지 함께 실행한다. 도구 자체가 게임의 주인공은 아니며, AI 생성물을 실제 게임에 안전하게 연결하기 위한 제작 안전장치다.

| OpenAI `gpt-4o-mini` | 모델명이 버전 | 런 blueprint 1순위 겸 일자 생성 2순위. 12일 시장 흐름과 세트 사건을 만든다 |

## 6. 주요 프롬프트 및 계약 방식

장문의 자연어 지시를 매번 전달하는 대신, 고정 규칙을 **하나의 계약서 파일**로
모았다. 파일은 `Runtime/contracts/compact-generation-contract.txt` 하나뿐이고,
검증기(`generation-server.js`)가 같은 파일을 근거로 결과를 검사한다. **지시와
검사가 갈라지지 않도록 계약을 두 곳에 두지 않는 것이 원칙이다.**

### 6.1 계약서를 절로 쪼개 필요한 것만 보낸다

계약서에는 `@ALL` · `@RUN` · `@DAY` 표식이 있고, 호출 모드에 따라 공통 절과
해당 모드 절만 조립해 보낸다.

```text
@ALL   227자   JSON·한글 규칙, ID 보존, 시대 배경
@RUN   887자   런 스키마, 세트 사건 규칙            → 런 호출에는 1,114자
@DAY 1,116자   일자 스키마, 길이·어미·카테고리 어휘 → 일자 호출에는 1,343자
```

**왜 필요했나.** 생성을 항목 단위로 쪼개자 호출 수가 늘었고, 쪼개기 전에는 한 번
실렸던 계약서가 한 판에 121번 실리게 되었다. 그때 계약서가 전체 입력의 74%를
차지했고, 그중 상당량은 그 호출에 쓸 일이 없는 규칙이었다 — LOT 하나를 만드는
호출이 세트 사건 규칙 695자를 매번 날랐다.

절을 나눈 뒤 **한 판 입력이 30.4% 줄었다.** 파일은 여전히 하나여서 갈라질
여지가 없고, 표식이 없는 계약서를 만나면 전부 `@ALL`로 들어가 예전과 같이
동작한다.

**표식 오타는 조용히 규칙을 지운다.** 어느 절에도 실리지 않은 줄이 생기면 모델은
규칙이 사라진 줄 모르고 답하고 검증기만 뒤늦게 떨어뜨린다. 그래서 **모든 줄이
적어도 한 모드에 실리는지 테스트가 확인한다.**

### 6.2 실제 계약서 (일자 생성 부분)

요약이 아니라 모델에게 그대로 가는 문장이다.

```text
Return one JSON object only. Write every user-facing text value in Korean.
Never output numeric game rules. Copy IDs exactly and preserve input order.

DAY: {schemaVersion:"1.0",day,marketHeadline,
      lots:[exactly 8 {lotId,displayName,description,rumor,setHint,npcReaction}]}.
Daily limits per item: displayName 20 Korean characters, description 70,
rumor 45, setHint 25, npcReaction 45. Use one sentence per text field.
Copy each input baseName exactly into displayName. Describe only visible
material, engraving, discoloration, repair, provenance mark, or wear.
Description must be one factual observation ending with one of:
"남아 있다.", "보인다.", "확인된다.", "이어진다.", "드러난다."
Vary the observed feature across all eight items and do not reuse the same
phrase three times. Never claim magic, supernatural powers, translation,
navigation, appraisal, market value, or gameplay effects as fact.
Category vocabulary: CER uses 유약/굽/몸체/손잡이/뚜껑/항아리/도자;
CLK uses 문자판/바늘/태엽/케이스/시계/크로노미터/유리돔/골격; ...
Describe the artifact, not the person or place depicted by its name.
```

### 6.3 형식은 지시가 아니라 검증기가 잡는다

문장으로 "마침표는 하나" 같은 형식을 지시해 봤지만 **이전과 같은 비율로 어겼다
(8건 중 1건).** 그래서 형식 강제는 프롬프트에서 빼고 검증기에 맡겼다.

검증기가 보는 것은 스키마·ID·개수·금지 수치에 더해 문구 품질이다 — 길이 초과,
허용 밖 어미, 카테고리 어휘 불일치, 한 문장 위반, 여덟 항목 간 중복이 모두
자동으로 걸린다. 걸린 항목은 6.4의 복구 호출로 넘어간다.

### 6.4 복구는 실패한 항목에만 보낸다

전체를 다시 만들지 않고 그 LOT 하나만 다시 만든다. 복구 프롬프트에는 **어긴
규칙과 그 LOT 입력만** 싣는다.

```text
RETRY_ERRORS:
lot 5 description has unsafe ending
<해당 모드의 계약 절>
INPUT LOT: {lotId, baseName, category, grade, setId}
```

실측에서 8개 중 6개가 이 경로로 살아났다. 하루치를 통째로 버리던 때와 비교하면
같은 실패에서 건지는 양이 다르다.

## 7. 측정 결과

모든 수치는 **배포된 엔드포인트에 실제로 요청을 보내** 얻었다. 시뮬레이션이나
추정이 아니다. 측정일은 2026-08-07~08이다.

### 7.1 배포 API 성공률과 지연

일자 생성(하루 8 LOT)을 시드만 바꿔 순차로 24판 호출했다.

| 지표 | 결과 |
|---|---|
| 실제 생성 | **23 / 24판** |
| 폴백으로 내려간 판 | 1 / 24 |
| **계약 검증 실패** | **0 / 24판** |
| 지연 중앙값 | **10.3초** |
| 지연 범위 | 8.0 ~ 20.1초 |

런 blueprint(프레임 + 세트 12개)는 15.1초에 완료되었고, 12개 세트의 사건 제목이
**12/12 모두 서로 달랐다** — 세트를 나눠 만들 때 이미 쓴 제목을 프롬프트에
실어 중복을 피하는 장치가 동작한다.

**폴백으로 내려간 1판의 사유도 로그로 확인했다.** 공급자 두 곳이 모두 응답
시간을 넘긴 경우였고(20초·8초), 인증 오류나 계약 위반이 아니었다.

### 7.2 입력량 감축

같은 결과를 얻는 데 드는 입력을 두 차례 줄였다.

| 조치 | 효과 |
|---|---|
| 계약서를 모드별 절로 분리 | 한 판 입력 **30.4% 감소** |
| 스키마의 항목 정의 반복 제거 | 일자 스키마 3,997 → **798자 (80% 감소)** |
| 〃 | 런 스키마 6,248 → **1,126자 (82% 감소)** |

두 번째 조치는 스키마가 8개 LOT의 정의를 여덟 번 반복하던 것을 하나로 합친
것이다. 일자 호출 하나가 6,117 → 2,918자가 되었고, **한 판 전체 입력이 약 15%
더 줄었다.** 줄인 뒤 16판을 다시 재어 계약 준수가 나빠지지 않았음을 확인했다.

### 7.3 폴백 품질

AI가 실패해도 게임이 멈추지 않는 것은 이전부터 확인된 사실이다. 이번에는
**폴백으로 나오는 문구 자체의 품질**을 측정했다.

| 지표 | 이전 (문자열 조합) | 현재 (사전 준비 문구) |
|---|---|---|
| 하루 8 LOT 중 중복 설명 | **매일 최소 2쌍** | **0건** |
| 하루 평균 서로 다른 문장 어미 | 2가지 | **3.99가지** |
| 하루 평균 서로 다른 첫머리 | — | **7.26 / 8** |
| 계약 검증 실패 | 0 | **0 / 600일** |

50개 시드 × 12일 = **600일치**를 검사한 결과다. 실제 생성의 어미가 8판 평균
4.6가지이므로, **폴백이 실제 생성에 근접한 다양성을 낸다.**

### 7.4 런마다 달라지는가 — 같은 품목, 다른 런

1장에서 세운 첫 목표는 "같은 게임 규칙 안에서 런마다 다른 추론 재료를 제공한다"
였다. 실제로 그런지 시드만 바꿔 1일차를 두 번 생성해 확인했다.

**엔진의 몫 — 일정 구성이 달라진다.** 8개 LOT 중 겹친 품목은 2개뿐이었다.

**생성의 몫 — 겹친 품목조차 다른 문장을 받는다.** 이쪽이 핵심이다.

> **붉은 장갑의 배우** (두 런에 모두 등장)
>
> | | 런 A | 런 B |
> |---|---|---|
> | 설명 | 액자 안쪽에 벗겨진 안료와 얇은 덧칠 자국이 남아 있다. | 화폭 가장자리에 붉은 안료가 번졌고 액자에 작은 보수 흔적이 남아 있다. |
> | 소문 | 무대 뒤에서 급히 손질했다는 말이 있다. | 초연 직후 극장 관리인이 맡겼다는 소문이 있다. |
> | 세트 힌트 | 붉은 색조 그림의 연결점 | 무대 초상화 연작 |

> **항로문 금은 상감함**
>
> | | 런 A | 런 B |
> |---|---|---|
> | 설명 | 황동 표면의 은제 상감선 사이로 어두운 녹이 확인된다. | 금속 표면에 금은 상감 선과 옅은 녹이 남아 있다. |
> | 소문 | 문양의 일부가 뒤늦게 덧대어졌다는 소문이다. | 경매장 장부에 봉인 표식이 있었다는 소문이다. |
> | 세트 힌트 | 금속 공예품 사이의 빈 고리 | 금속 공예품과 어울림 |

**세트 힌트가 달라지는 것이 게임에는 가장 크다.** 플레이어는 이 문구로 어떤
물품끼리 묶이는지 추론하므로, 같은 물품이라도 런마다 다른 실마리를 준다.

**덜 달라지는 것도 있다.** 시장 헤드라인은 두 런이 거의 같았다 — "안개 속
경매장에 오래된 항구의 흔적이 모였다" 와 "안개 낀 경매장에 항구의 오래된 흔적이
모인다." 하루에 하나뿐인 필드라 표현 폭이 좁고, LOT 문구만큼 갈리지 않는다.

### 7.5 게임 및 하네스 검증

- 게임 런타임 테스트 **109건 전부 통과**
- 생성 연결 점검(`npm run audit:generation`) 오류 0건
- 900개 시드에서 86,400 LOT 일정 생성, 잘못된 12일 일정 0건
- 생성 결과의 엔진 소유 수치 침범 0건
- 브라우저에서 배포본을 열어 런 blueprint와 1~3일차 생성 수신까지 확인

### 7.6 수치 해석의 한계

**표본이 작다.** 24판은 통계가 아니라 관찰이다. 실제로 이 프로젝트는 같은
함정을 한 번 겪었다 — 스키마를 줄인 뒤 8판을 재고 "지연 중앙값이 10.9초에서
9.4초로 좋아졌다"고 적었는데, 8판을 더 재니 11.4초가 나와 합친 중앙값이
10.3초였다. **8판으로 성능 변화를 단정할 수 없다는 것이 이 과정에서 확인한
사실이고, 위 표의 지연 수치도 같은 눈으로 읽어야 한다.**

그래서 주장하지 않는 것과 주장하는 것을 나눈다.

- **주장하지 않는다** — 지연이 개선되었다, 폴백률이 낮아졌다
- **주장한다** — 입력량이 줄었고(측정 가능), 계약 준수가 24판 내내 깨지지
  않았으며(0/24), 폴백 문구의 중복이 구조적으로 사라졌다(600일 검사)

## 8. 실제 프로젝트에 미친 영향

### 적용 전

- UI 목업, 기획 문서와 밸런싱 자료가 실제 게임 상태와 분리되어 있었다.
- 생성 AI 요청·응답의 명시적 계약과 실패 처리 방식이 없었다.
- VSL 최종 결과를 받기 전에는 시스템 연결 작업을 시작하기 어려웠다.

### 현재

- VSL과 무관하게 12일 진행을 검증할 수 있는 모듈형 런타임이 존재한다.
- 경매·감정·판매·의뢰·경제·대출·결산이 같은 상태 데이터를 공유한다.
- VSL 요소를 교체할 어댑터와 좌표 매핑 계약이 준비되어 있다.
- 생성·검증·재시도 경로를 실제 모델로 확인했다.
- AI가 없어도 폴백으로 12일 진행이 중단되지 않는다.
