## 1. 현행 진단

### 1-1. 지금 보상이 어떻게 계산되는가

`systems.js:217-231` `deliverQuestItem()`

```js
item.delivered = true; item.sold = true; item.salePrice = 0;   // 물건은 태운다
const completionBonus = questCompletionBonus(quest, state.shopStage);
const reward = quest.rewardMode === 'deliveredBasePlusFeePlusBonus'
  ? item.basePrice + quest.fee + completionBonus                // ← 이 분기가 돈다
  : Math.round(quest.reward * (1 + shopBonus));
```

세 항목이다.

| 항목 | 현재 값 | 출처 |
|---|---|---|
| `item.basePrice` | 제출한 물품의 공개 기준가 | 물건이 소모되므로 보전 |
| `quest.fee` | **0** | `grade-*`/`category-*` 가 balance.json 에 정의가 없어 `submissionDefaults.fee` 로 떨어진다 |
| `completionBonus` | **3,000 / 4,500 / 6,000 / 7,500** | `rewardPolicy.completionBonusByStage[상회단계]` — 등급·계열 무관 절대치 |

즉 **현행 보상 = 제출 물품 기준가 + 완료보너스(단계별 절대치)** 다.
"의뢰 보상 7,500" 은 세 항목 중 하나일 뿐이다.

### 1-2. 무엇이 망가졌나

4단계 · 10~12일차 (기준가 = 등급중심값 × 일차배율 1.25)

| 등급 | 기준가 | 낙찰가 | 현행 보상 | **현행 순익** |
|---|---:|---:|---|---:|
| 일반 | 1,900 | 2,075 | 1,900 + 7,500 = 9,400 | **+7,325** |
| 희귀 | 5,000 | 6,013 | 5,000 + 7,500 = 12,500 | **+6,487** |
| 영웅 | 15,000 | 18,864 | 15,000 + 7,500 = 22,500 | **+3,636** |
| 전설 | 31,300 | 38,130 | 31,300 + 7,500 = 38,800 | **+670** |

순익 = 보상 − 낙찰가. 등급이 올라갈수록 **줄어든다**. 완전한 역진 구조다.

낙찰가 검산 (전설, 4단계) — `systems.js:62-76`, `:119-129`

```
publicEstimate = 31,300 × 1.05(expectedDemand)                = 32,865
maxBid         = 32,865 × 1.1(전설계수) × factor(0.78~1.08)   = 28,198 ~ 39,044
cap            = bots.capitalByStage[4]                       = 35,000   ← 여기서 잘린다
최소 낙찰가     = 35,000 + round(31,300 × minRaiseRate 0.1)    = 38,130
```

**전설은 봇 자본 상한 때문에 낙찰가가 사실상 35,000+ 로 고정**인데 보상은
기준가에 7,500 만 얹으니 살수록 손해에 가깝다.
단계 대표 기준가(29,700)로 재면 **−770 으로 마이너스**다.

고칠 지점은 보너스의 크기가 아니라 **부착 지점**이다.
단계에만 붙어 있던 것을 **의뢰 종류와 제출 등급에도** 붙인다.

## 3. 보상표

```
보상 = 제출 물품 기준가(item.basePrice) + 수주비(fee) + 완료보너스
완료보너스 = completionBonus[의뢰 종류][제출 물품 등급][상회 단계]
```

- 기준가는 **제출한 그 물품의 실제 `basePrice`** 다. 등급 중심값이 아니다.
- 수주비는 완료 시 전액 환급한다(`refundAcceptanceFee: true` 유지).
  **수주비는 실패했을 때만 손해다.**
- 등급 제출 의뢰는 제출 등급이 의뢰 등급과 항상 같으므로 조회 경로가 같다.
  계열 제출 의뢰만 제출 등급에 따라 갈린다.

### 3-1. 등급 제출 의뢰 — 완료보너스

|---|---:|---:|---:|---:|
| 일반 등급 제출 | **250** | **450** | **800** | **1,250** |
| 희귀 등급 제출 | **650** | **1,300** | **2,350** | **3,650** |
| 영웅 등급 제출 | **2,150** | **4,300** | **7,650** | **12,000** |
| 전설 등급 제출 | **4,900** | **9,750** | **17,300** | **27,000** |

### 3-2. 계열 제출 의뢰 (6종 공통) — 완료보너스

| 제출 등급 | 1단계 | 2단계 | 3단계 | 4단계 |

일차나 단계에 따라 올리지 않는다. 후반으로 갈수록 상대적으로 가벼워지는데 그건 의도한 곡선이다.

## 4. 이 숫자들이 어디서 나왔나

표는 손으로 찍은 게 아니라 아래 식을 단계 대표 일차에 넣고 50원 단위로 반올림한 것이다.
튜닝할 때 이 식을 만지면 표 전체가 일관되게 움직인다.

```
완료보너스 = 등급중심값 × 대표일차배율[단계] × 단계계수[단계] × 등급계수[등급] × 종류계수[의뢰종류]
```

| 항목 | 값 | 근거 |
|---|---|---|
| 등급중심값 | 1,500 / 4,000 / 12,000 / 25,000 | `balance.gradeBase` |
| 대표일차배율 | 0.500 / 0.667 / 0.917 / 1.188 | 마감 규칙상 1단계=1~2일 · 2단계=3~5일 · 3단계=6~8일 · 4단계=9~12일. 각 구간의 `shop.priceMultiplierByDayStage` 평균 |
| **단계계수** | **0.30 / 0.45 / 0.58 / 0.70** | 아래 4-1 |
| **등급계수** | **1.00 / 1.10 / 1.20 / 1.30** | 아래 4-2 |
| **종류계수** | 등급 제출 **1.00** · 계열 제출 **0.70** | 아래 4-3 |

### 4-1. 단계계수 `0.30 / 0.45 / 0.58 / 0.70`

기준선은 **페어 판매 배수 − 1** 이다.
페어 판매 배수 = `1.2 × (1 + shop.setBonus[단계]) × (1 − shop.auctionFee[단계])`
= 1.254 / 1.397 / 1.544 / 1.680 → −1 하면 **0.254 / 0.397 / 0.544 / 0.680**.

여기서 앞단만 올리고 뒷단은 그대로 뒀다.

- **앞을 올린 이유** — 1~2일차는 페어를 팔아도 순익이 100~400원이다. 2단계 승급 조건상
  의뢰 1건은 반드시 해야 하는데(`shop.questRequirement[1] = 1`), 기준선 그대로면 그 1건이 세금이 된다.
- **뒤를 안 올린 이유** — 현행이 무너진 지점이 정확히 여기다. 단계 1→4 증가폭이
  현행 ×2.5(3,000→7,500) 인데 ×2.33(0.30→0.70) 으로 낮췄다.
  절대 금액의 후반 인플레는 기준가에 붙은 일차배율(×1.25)이 이미 담당한다.

### 4-2. 등급계수 `1.00 / 1.10 / 1.20 / 1.30`

확보 난이도 프리미엄이다. 물량 가중치가 0.25 / 0.375 / 0.25 / 0.125 이고
고등급일수록 봇 경쟁이 붙고 현금이 묶인다.

**+0.10 씩만 올린 것이 의도다.** 계수 자체는 완만해도 곱해지는 등급중심값이
1,500 → 25,000 이라 절대 보너스는 저절로 250 → 4,900(1단계) / 1,250 → 27,000(4단계) 로 벌어진다.
여기서 계수까지 크게 벌리면 전설 의뢰 하나가 풀하우스를 넘어선다.

### 4-3. 종류계수 — 계열 제출 `0.70`

**세트(페어 = 같은 계열 2점)가 계열 의뢰보다 어려우므로 세트가 상위 보상을 받아야 한다.**
0.70 은 그 순서가 **전 단계·전 등급에서 뒤집히지 않는 상한**이다.

그 결과 계열 의뢰는 **무족보 판매와 페어 판매 사이**에 정확히 앉는다(5-1 참고).
"족보를 못 세우겠으면 계열 의뢰, 세울 수 있으면 팔아라" 가 한 줄로 성립한다.

계열 의뢰가 **제출 등급을 보는 것**도 여기서 나온다. 등급을 안 보면 6개 계열 의뢰
전부에 제일 싼 일반을 던지는 게 최적이 되고, 의뢰소가 쓰레기 처리장이 된다.

### 4-4. 반올림 잔차

50원 단위 반올림이라 표 값이 식의 결과와 최대 25원 어긋난다.
눈에 띄는 곳은 **일반 1단계 250원**(식으로는 225) 하나인데, 위로 올린 것은 의도다 —
1단계 일반 의뢰는 승급을 위해 반드시 한 번 해야 하는 자리라 여유를 줬다.

## 5. 검증 — 의뢰와 세트 중 어느 쪽도 정답이 아니다

### 5-1. 보상 배수 대 판매 배수 (둘 다 기준가 대비, 수주비 제외 · 단계 대표 일차 기준)

판매 배수 = 족보배수 × (1 + `shop.setBonus[단계]`) × (1 − `shop.auctionFee[단계]`)

| 단계 | 무족보 | **계열의뢰 일/희/영/전** | 페어 | **등급의뢰 일/희/영/전** | 트리플 | 풀하우스 |
|---|---:|---|---:|---|---:|---:|
| 1 | 1.04 | **1.20 / 1.23 / 1.25 / 1.27** | 1.25 | **1.33 / 1.32 / 1.36 / 1.39** | 1.36 | 1.57 |
| 2 | 1.16 | **1.30 / 1.34 / 1.38 / 1.41** | 1.40 | **1.45 / 1.49 / 1.54 / 1.58** | 1.51 | 1.75 |
| 3 | 1.29 | **1.40 / 1.45 / 1.49 / 1.53** | 1.54 | **1.58 / 1.64 / 1.70 / 1.75** | 1.67 | 1.93 |
| 4 | 1.40 | **1.48 / 1.54 / 1.59 / 1.64** | 1.68 | **1.70 / 1.77 / 1.84 / 1.91** | 1.82 | 2.10 |

읽는 법.

- **계열 의뢰는 전 구간에서 무족보와 페어 사이**다. 족보가 서면 파는 게 항상 낫고, 안 서면 의뢰가 낫다.
- **등급 의뢰는 페어보다 조금 위, 트리플 언저리, 풀하우스보다 확실히 아래**다.
  최고치인 전설·4단계 1.91 도 풀하우스 2.10 의 91% 다.
- 등급 의뢰가 페어보다 위인 이유는 **지정된 등급을 따와야** 하기 때문이다.
  계열은 등급을 안 가려서 언제든 채울 수 있으므로 페어 아래가 맞다.

### 5-2. 몰빵이 안 되는 이유

**의뢰 몰빵이 안 되는 이유** — 제출한 물품은 족보에서 빠진다.
4단계에서 풀하우스가 서 있는데 전설을 의뢰에 넘기면
(1) 그 전설이 65,730 대신 60,800 이 되고
(2) 풀하우스가 깨져 나머지 5점이 2.10 대신 1.68 로 팔린다.
나머지 5점 기준가 합이 10,000 만 돼도 (2)에서만 4,200 이 날아간다.
**족보가 서 있으면 파는 게 항상 낫다.**

**세트 몰빵이 안 되는 이유** — 세트 배수를 만드는 것이 상회 단계인데
(`shop.setBonus`), 상회 승급 조건이 **완료 의뢰 수**다(`shop.questRequirement`).
보관칸도 상회 단계에서 나온다.

### 5-3. 시세를 넣으면 판단이 갈린다

판매가는 계열 시세지수(`market`, 평균 1.00 · 표준편차 약 0.105)를 곱하지만
**의뢰 보상은 시세를 안 탄다.** 그래서 "오늘 이 계열 시세가 어떤가" 가
팔지 제출할지를 가른다.

의뢰가 페어 판매를 이기기 시작하는 시세지수와 그 확률(4단계 기준):

| | 일반 | 희귀 | 영웅 | 전설 |
|---|---|---|---|---|
| 등급 의뢰 | 1.01 (55%) | 1.05 (70%) | 1.10 (82%) | 1.14 (91%) |
| 계열 의뢰 | 0.88 (13%) | 0.92 (23%) | 0.95 (32%) | 0.98 (43%) |

등급 의뢰도 일반은 거의 반반이고, 계열 의뢰는 시세가 눌린 날의 도구다.
어느 쪽도 자동 선택이 아니다.

| 1.0건/일 | 약 29,000 | 약 204,000 | 12.4% |

## 7. 제시 · 수주 규칙

수치만으로는 안 잡히는 부분이다. 두 가지가 같이 들어가야 위 표가 성립한다.

### 7-1. 하루 제시 구성 — 등급 1 + 계열 1 + 무작위 1

지금은 10종을 섞어서 앞에서 3개를 자른다(`systems.js:31-32`). 그러면 계열이 10종 중
6종이라 **제시 3건 중 평균 1.8건이 계열**이고, 등급 의뢰가 아예 안 뜨는 날이 생긴다.
전설 의뢰가 화면에 안 뜨면 3-1 표의 등급 구배가 플레이에 안 닿는다.

```
제시 3건 = 등급 4종 중 1건 + 계열 6종 중 1건 + 남은 8종 중 1건
왕실 인가장(royal-charter) 보유 시 5건 = 등급 2건 + 계열 2건 + 남은 6종 중 1건
```

중복 없음. 기존처럼 `createRng(`${seed}:quests:${day}`)` 로 결정론 유지.

### 7-2. 동시 진행 의뢰 상한 3건 — **현재 코드에 없다**

`balance.json` 의 `quests.offering.acceptMax` 는 3인데 `acceptQuest()` 가 이 값을
안 본다(`systems.js:190-196`). 상한이 없으면 마감이 2일이라 최대 9건이 동시에 굴러가고,
5-4 의 기여도 추정이 무너진다.

```
미완료 activeQuests 가 acceptMax(3) 이상이면 수주 거부
```

**이건 밸런스 수치가 아니라 규칙이지만, 이게 없으면 위 수치가 의미를 잃는다.**

### 7-3. 그대로 두는 것

- 마감 — 수주일 +2일 (`deadlineDay = min(13, day + 2)`)
- 물품 하나는 한 의뢰에만 제출 (`item.delivered` 로 이미 막혀 있다)
- 의뢰 간 수주 충돌 없음 (`acceptancePolicy`)
- 승급 조건 `shop.questRequirement: [0, 1, 2, 3]` — 11절 참고

## 10. 화면 표기

### 10-1. 의뢰 카드의 보상

보상이 제출 물품 기준가를 포함하므로 단일 금액을 못 쓴다. 종류별로 나눈다.

**등급 제출 의뢰** — 등급이 고정이라 그날 기준가가 거의 정해져 있다. 예상액을 쓴다.

```
보상  약 3,350원   (기준가 + 수주비 + 완료보너스 1,250)
```

예상액 = `등급중심값 × shop.priceMultiplierByDayStage[일차구간] + 수주비 + 완료보너스`.
`publicPriceVariation` ±10% 때문에 "약" 을 붙인다.

**계열 제출 의뢰** — 어떤 등급을 넣느냐로 갈린다. 구간으로 쓴다.

```
보상  3,150 ~ 50,600원   (제출 등급에 따라)
```

`quest-detail-dialog` 에서는 등급별 4줄 표로 펼친다.

### 10-2. 제출 직전 확정 표시

`renderQuestOffice` 의 제출 `select` 에서 물품을 고르면 그 자리에서 확정 보상을 보인다.
지금 구조에서 가장 값싸게 넣을 수 있는 정보이고, 위 "구간" 표기의 모호함을 없앤다.

```
[제출할 물품 선택 ▾]  →  받을 금액 23,800원
```

### 10-3. 아이콘

등급 4종이 지금 레거시 아이콘을 돌려쓰고 있다
(`grade-COMMON → restraint`, `grade-RARE → multi`, `grade-EPIC → block`,
`grade-LEGENDARY → designated`). 계열 6종은 계열 아이콘을 그대로 쓴다.

등급 4종 전용 아이콘은 아트 작업이 필요하다. 급하지 않으면 현행 매핑 유지.

## 11. 판단이 필요한 것 · 재측정 항목

1. **`shop.questRequirement` 를 올릴지.**
   지금 `[0, 1, 2, 3]` — 여정 전체에서 3건이면 최고 단계까지 간다. 의뢰가 10종으로
   늘고 하루 3건씩 뜨는데 요구치가 3건이면 게이트로서 무게가 없다.
   `[0, 1, 3, 5]` 정도가 후보인데, 이건 곧바로 마감 실패율(현행 32.1%)을 올린다.
   **시뮬 재측정 없이는 바꾸지 말 것.** 기본은 현행 유지로 뒀다.

2. **왕실 인가장(royal-charter) 값어치.**
   실측 73,640 은 "의뢰 5종 전부 제시" 기준이다. 이제 10종이라 5건 제시는
   전부가 아니라 절반이고, 등급 2 + 계열 2 + 무작위 1 구성이면 효과의 성격도 바뀐다.
   재측정 대상이다.

3. **단계 안에서 일차가 움직이면 생기는 편차.**
   보너스가 절대치라 단계 대표 일차에서 정확하고 그 앞뒤로 ±10% 안팎 흔들린다.
   예: 4단계 일반 등급 의뢰 순익이 9일차 +1,112, 10~12일차 +1,075.
   같은 단계 안에서는 **이른 일차가 조금 유리**하다. 의도한 부작용은 아니지만
   크기가 작고, 절대치 표를 쓰는 이상 피할 수 없다.

4. **낙찰가 추정의 한계.**
   6절의 낙찰가는 봇 3기가 평균적으로 경쟁했을 때의 값이다. 실제로는 봇 계수가
   `0.78~1.08` 로 흔들려 싸게 잡히는 날이 있고, 사람은 그런 날만 고른다.
   그래서 표의 순익은 **하한에 가깝다.** 다만 의뢰든 판매든 낙찰가는 공통이라
   두 경로의 우열 비교(5-1, 5-3)는 낙찰가 가정과 무관하게 성립한다.

5. **시뮬레이터(`sim/v6-sim.js`) 반영.**
   `balance.json` 을 읽는 구조이므로 보상 조회 부분만 고치면 된다.
   반영 후 `measurementPolicy.baseline` 로 씨앗 900개를 다시 돌려
   도달률 · 마감실패 · 생존중앙값 · `questsPerRun` 을 갱신한다.
   목표 밴드는 기존과 같다 — 도달 45~60%.
