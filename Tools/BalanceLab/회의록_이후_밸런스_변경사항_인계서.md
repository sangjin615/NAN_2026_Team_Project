### 1.4 납품형 의뢰 보상

최종 공식:

```text
완료 지급액 = 제출 물품의 확정 기준가 + 수주비 환급 + 단계별 완료 보너스
플레이어 순이익 = 제출 물품 기준가 + 단계별 완료 보너스 - 실제 구매비용
```

| 상회 단계 | 완료 보너스 |
|---|---:|
| 1단계 | 3,000G |
| 2단계 | 4,500G |
| 3단계 | 6,000G |
| 4단계 | 7,500G |

```text
completionBonusByStage = [0, 3000, 4500, 6000, 7500]
```

- 수주비는 의뢰 수락 시 먼저 차감하고, 성공 시 전액 환급한다.
- 실패 시 수주비는 환급하지 않는다.
- 제출한 물품은 소모한다.
- 별도의 기존 `shop.questBonus`는 납품 완료 보너스에 중복 적용하지 않는다.
- `quests.*.reward` 고정값은 구형 행동형 시뮬레이터 호환값이며 실제 납품 보상으로 사용하지 않는다.

목적: 초반의 건당 약 3,000G 이익은 유지하면서, 업그레이드 총비용 37,000G를 지불한 뒤 최종 경매 자금이 남도록 후반 의뢰 이익을 확대한다.

|---|---:|---:|
| 1단계 | 8,000G | 24,000G |
| 2단계 | 12,000G | 36,000G |
| 3단계 | 16,000G | 48,000G |
| 4단계 | 20,000G | 60,000G |

```text

```

- 갈레오, 모이라, 이네스 모두 같은 단계 자금으로 하루를 시작한다.

목적: 기존 프로토타입에서 경쟁자 1명당 약 3만~3.6만G, 세 명 합계 10만G 이상이 책정되어 하루 8회 경매 동안 자금이 사실상 고갈되지 않았던 문제를 해결한다.

## 2. Runtime 로직 변경 명세

### 2.1 물품 가격 확정 시점

1. 원본 카탈로그 가격은 `catalogBasePrice`로 보존한다.
2. 물품이 해당 날짜의 경매품으로 출품될 때 현재 상회 단계의 물가 배율을 한 번 적용한다.
3. 결과를 해당 물품의 `basePrice`로 저장한다.
4. 이후 상회가 승급해도 이미 출품됐거나 낙찰된 물품의 `basePrice`를 다시 계산하지 않는다.
5. 감정비, 처분가, 대출 담보가, 의뢰 납품 보상은 이 확정된 `basePrice`를 사용한다.

주의: 화면을 다시 열 때마다 원본 가격에 배율을 재적용하면 중복 인플레이션이 발생한다. 가격 계산은 출품 생성 시 한 번만 수행해야 한다.

### 2.2 대출 처리

대출 가능 조건:

- 상회 2단계 이상
- 진행 중인 대출 없음
- 담보로 잡을 수 있는 미판매 물품 존재
- 담보 물품이 다른 시스템에 잠겨 있지 않음
- `currentDay + 3 <= 12`; 정상 여정 밖으로 만기가 넘어가는 늦은 대출 금지

담보 중 제한:

- 판매 불가
- 감정 불가
- 의뢰 제출 불가
- 다른 대출의 담보로 중복 사용 불가

만기 처리:

1. 현금이 만기 상환액 이상이면 자동 상환하고 담보 잠금을 해제한다.
2. 부족하면 담보를 압류한다.
3. 압류 담보의 공개 기준가를 상환액에 충당한다.
4. 그래도 부족한 금액은 플레이어 현금에서 추가 차감한다.
5. 연체 시 조합 거래 제한 상태를 적용한다.

### 2.3 의뢰 완료 처리

의뢰 수락:

```text
cash -= acceptanceFee
```

납품 성공:

```text
bonus = completionBonusByStage[currentShopStage]
reward = deliveredItem.basePrice + acceptanceFee + bonus
cash += reward
inventory.remove(deliveredItem)
```

검증 조건:

- 제출 물품이 의뢰 조건을 만족해야 한다.
- 담보로 잠긴 물품은 제출할 수 없다.
- 물품 하나는 의뢰 하나에만 제출할 수 있다.
- 납품 보상에 기존 상회 의뢰 보너스를 다시 곱하지 않는다.

### 2.4 경쟁자 자금 처리

기존 Runtime의 다음 방식은 제거한다.

```text
당일 경매품별 최대 입찰가 합계 × 60%
25,000 × 1.155^day
```

새 방식:

```text
dailyBudget = capitalByStage[currentShopStage]
remainingBudget[competitorId] = dailyBudget
```

각 경매의 경쟁자 최대 입찰가는 다음 두 값 중 작은 값이다.

```text
maxBid = min(가치평가 기반 입찰 상한, remainingBudget[competitorId])
```

낙찰 시:

```text
remainingBudget[winnerId] -= finalPrice
```

일차가 끝나고 다음 날이 시작되면 새 상회 단계 기준으로 당일 자금을 다시 배정한다. 경매 참가자 UI의 `추정 자산`에는 계산용 가상 총액이 아니라 실제 `remainingBudget`을 표시한다.

## 3. 기존 Runtime에서 제거하거나 대체할 항목

- `bots.nemesisInitial = 25000` 기반 일차별 복리 자금 산식
- `bots.growthPerDay = 1.155` 기반 자금 증가
- `estimateBotDailyAssets()`의 `sum(maxBid) * 0.6` 자산 산정
- 납품 의뢰의 고정 `+3,000G` 완료 보너스
- 납품 보상에 `shop.questBonus`를 곱하는 처리
- 상회 승급 시 보유 물품까지 현재 단계 가격으로 재평가하는 처리

구형 필드는 이전 저장 데이터 또는 시뮬레이터 호환이 필요하면 남겨도 되지만, 신규 Runtime 계산에서는 참조하지 않아야 한다.

## 4. 저장 데이터 호환

기존 저장 파일에 신규 필드가 없을 수 있으므로 로드 시 다음을 보정한다.

- 경매 출품/보유 물품에 `catalogBasePrice`가 없으면 현재 `basePrice`를 원본값으로 간주하여 한 번만 채운다.
- 경쟁자 `remainingBudget`이 없으면 현재 상회 단계의 `capitalByStage`로 초기화한다.
- 진행 중 대출에 `earlyRepayment`가 없으면 `principal × 1.05`로 계산한다.
- 이미 출품되거나 보유한 물품에는 로드 시 물가 배율을 다시 곱하지 않는다.

## 6. 현재 측정 결과와 주의사항

복사본 밸런싱 랩에서 경쟁자 자금을 낮추고 낙찰 차감을 적용한 뒤 5,000회 측정한 결과:

- 목표 도달률: 76.2%
- 마감 실패율: 14.3%
- 파산율: 0%
- 생존자 중앙 자산: 464,100G

기존 승인 목표는 도달률 45~60%, 생존자 중앙 자산 250,000G 이하였으므로 현재 조합은 상당히 쉬운 상태다. 특히 밸런싱 랩의 구형 의뢰 시뮬레이션은 실제 납품 물품 소모와 단계별 완료 보너스를 완전히 재현하지 않는다. 따라서 Runtime 로직 이식 후 실제 납품 방식으로 다시 측정하고, 필요하면 경쟁자 자금 또는 후반 완료 보너스를 재조정해야 한다.
